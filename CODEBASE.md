## What this app does

Families share gift lists. Members can claim gifts on behalf of one another so purchases aren't duplicated. The gift owner never sees who claimed or bought their gifts — this "surprise preservation" is enforced at the Postgres RLS layer, not just the UI.

## Database schema

App tables live in `public`, with RLS enabled on every one. `src/db/schema.ts` is the source of truth; the tables below keep their Supabase-era columns.

Better Auth's tables (`user`, `session`, `account`, `verification`, `rate_limit`) sit beside them with UUID ids; `profiles.id` references `user.id`, and Better Auth's user hooks keep `profiles` in step. Only `auth_service` can reach them.

RLS reads the current user through `auth.uid()`, a shim that returns `current_setting('app.user_id', true)`. `withUser()` sets it for one transaction; with nothing set, every app table returns zero rows to `app_user` (`profiles` included: its Supabase policy was `USING (true)`). The only ways past RLS are SECURITY DEFINER functions (`drizzle/0001_roles_rls_functions.sql`): `create_family`, `create_invite`, `accept_invite`, `join_family`, and, for signed-out landing pages, `invite_preview` and `join_preview`; plus `take_rate_limit` (`drizzle/0006`), which touches only the rate-limit counters. Policies use two definer helpers that only answer yes or no: `is_family_member` (`0001`) and `shares_family_with` (`0007`).

### `profiles`
Auto-created on signup via the `handle_new_user` trigger. Mirrors `auth.users`.

RLS (`profiles_select`, narrowed in `drizzle/0007`, #160): you read your own profile and the profiles of people who share at least one family with you, nobody else's. Leaving or being removed from the last shared family ends it both ways. The check is `shares_family_with(_user_id)`, a SECURITY DEFINER function that reads the caller from `auth.uid()` (so it can't be asked about two other people) and reads `family_members` without its policy, so there is no policy recursion. `invite_preview` still returns the inviter's name to a stranger, because it is a definer function. `profiles_update_own` and `auth_service`'s policy are unchanged. `/members/[userId]` 404s when the profile read comes back empty. `tests/db/policies.test.ts` ("profile visibility") and `tests/db/member-page.test.ts` cover it.

| Column | Type | Notes |
|---|---|---|
| id | uuid PK | FK → auth.users |
| email | text | |
| name | text | from signup metadata |
| avatar_url | text | nullable |

### `families`
A family group. One user creates it and becomes the owner.

| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| name | text | |
| created_by | uuid | FK → profiles |
| invite_code | text | unique code for the shareable `/join/<code>` link. New codes are 32 hex characters (122 random bits, default `replace(gen_random_uuid()::text, '-', '')`, migration `0006`); older ones are 12 characters and keep working until reset. The owner resets it with `resetJoinCode` (`SET invite_code = DEFAULT` through `families_update_owner`); the old code stops working at once, and members already in stay in |

The `handle_family_created` trigger inserts a `family_members` row with `role = 'owner'` on insert.

### `family_members`
Junction table. A user can belong to multiple families.

| Column | Type | Notes |
|---|---|---|
| family_id | uuid | FK → families |
| user_id | uuid | FK → profiles |
| role | text | `'owner'` or `'member'` |

| expires_at | timestamptz | now + 7 days |

### `gifts`
A gift on someone's personal wishlist (not scoped to a single family — visible to anyone who shares any family with the owner; see design decision below).

| Column | Type | Notes |
|---|---|---|
| owner_id | uuid | the person who wants this gift |
| title | text | |
| description | text | nullable |
| price | numeric | nullable |
| url | text | nullable |
| image_url | text | nullable |
| source | text | `'manual'` now; reserved for `'chrome_extension'`, `'google_sheets'` |

### `gift_claims`
Records who is buying a gift. The one-row-per-gift UNIQUE constraint prevents double-claiming.

| Column | Type | Notes |
|---|---|---|
| gift_id | uuid UNIQUE | |
| claimed_by | uuid | |
| status | text | `'claimed'` or `'purchased'` |

**Critical RLS policy** (`gift_claims_select`): a user sees a claim if they made it, or if they share a family with the gift's owner and are not the owner. Owners are blind to claims on their own gifts at the database level; `tests/db/policies.test.ts` proves it on every PR.

### `onboarding`
One row per person, made by the first tour event; no row means brand new. The signed-in layout reads it (`getTour`) and hands it to `TourProvider`, and `TourUi` draws the walk and First Steps from it (see "Onboarding tour" under Design decisions). Migration `0005`.

| Column | Type | Notes |
|---|---|---|
| user_id | uuid PK | FK → `profiles.id`, ON DELETE CASCADE |
| walk_ended_at | timestamptz | nullable; set when the walk is finished or skipped |
| walk_outcome | text | nullable; `'completed'` or `'skipped'` |
| peeked_at | timestamptz | nullable; opened someone's list after the walk |
| secret_seen_at | timestamptz | nullable; opened the surprise explainer |
| hints_read | text[] | not null, default `{}`; ids of dismissed hints |
| steps_ended_at | timestamptz | nullable; set when the steps are all done or hidden |
| steps_outcome | text | nullable; `'completed'` or `'hidden'` |
| steps_track | text | nullable; `'invited'` or `'solo'`, chosen when the steps first show |
| restarted_at | timestamptz | nullable; set by replay, drives the "welcome back" wording |
| created_at, updated_at | timestamptz | not null, default `now()` |

RLS is own-row only: `onboarding_select_own`, `onboarding_insert_own` and `onboarding_update_own` (`auth.uid() = user_id`), no delete policy (rows go with the profile), and no access for `auth_service`. It is its own table, not columns on `profiles`, because `profiles_select` let every signed-in person read every profile row when it was added (now family members can, since `0007`) and the tour's state is nobody else's business; it also leaves `auth_service`'s column grants on `profiles` alone. The server sets every time, and the first outcome wins.

### `app_rate_limit`
The app's own rate-limit counters (migration `0006`, #154), one fixed window per key. Better Auth's `rate_limit` covers only `/api/auth`. RLS is on with no policies and `app_user` has no grants: it reaches the table only through `take_rate_limit(key, limit, window_seconds)`, a definer function that counts one hit and returns `allowed` and `retry_after` (seconds), so signed-out join previews can count too. Now and then (1 call in 100) it deletes keys whose window ended over an hour ago. See "Why the app rate-limits joins and invites" under Design decisions.

| Column | Type | Notes |
|---|---|---|
| key | text PK | `<action>:<scope>:<id>`, for example `invite:family-day:<familyId>` |
| count | integer | hits in the current window |
| reset_at | timestamptz | when the window ends; indexed for the cleanup |

## Route structure

```
/                        → public marketing page (static); signed-in people are redirected to /dashboard by the proxy
/robots.txt              → src/app/robots.ts, answered per request: "Disallow: /" unless APP_ENV is prod
/opengraph-image.png     → the social card (a committed PNG, src/app/opengraph-image.png)
/login                   → email/password sign in
/signup                  → create account
/forgot-password         → request a password-reset email
/reset-password          → set a new password (the emailed link carries a token; no session needed)
/dashboard               → Home: yellow hero (greeting, summary, Add a gift / See my list), "You're shopping for" (`ShoppingCard`: own claims with progress and Mark bought), "Your people" scroller, family cards, "surprises stay secret" note
/families                → list all families for the current user
/families/new            → create a family
/families/[familyId]     → family hub: hero header with avatar stack, Invite someone (every member; opens a bottom sheet with the link and email form), owner-only Settings, "Everyone's lists" rows
/families/[familyId]/settings  → family settings (task 10): owners get rename, members with Remove, and a Danger zone (delete); non-owners get a read-only view with a note; everyone gets the Invite sheet
/gifts                   → manage your own list (no claim data shown)
/gifts/new               → add a gift
/gifts/[giftId]/edit     → edit a gift
/members/[userId]        → someone's list (restyled, #54 05a; a 404 unless you share a family with them, #160): avatar header "<shortName>'s list" with up-for-grabs count and surprise banner (`MemberListHeader`), All / Up for grabs / Mine filter and a 1/2/3-column `TheirGiftCard` grid (`TheirGiftList`, client; #54 05c), back link always shown (family if `?familyId`, else /dashboard)
/invite/[token]          → email invite acceptance (no auth gate)
/join/[inviteCode]       → shareable link acceptance (no auth gate); each look counts against the visitor's IP (prod), with a "Too many tries" page past the limit
/account                 → your account (#54 task 11): profile card, change name, change password, sign out, theme picker, replay the tour (`ReplayTourCard`, #98)
/privacy                 → the Privacy Policy, rendered from docs/legal/lumen-privacy-policy.md (static, `force-static`); published since `LEGAL_EFFECTIVE_DATE` was set (2026-10-13)
/terms                   → the Terms of Service, same, from docs/legal/lumen-terms-of-service.md
```

Route groups:
- `(auth)/` — unauthenticated pages, no nav
- `(legal)/` — `/privacy` and `/terms`: public, static, under their own layout (`SiteHeader`, `<main id="main">`, `SiteFooter legal={legalPublished()}`), outside the signed-in shell
- `(app)/` — auth-gated pages; `layout.tsx` redirects to `/login` if no session
- `(app)/loading.tsx` — skeleton for signed-in pages (shadcn `Skeleton`, shaped like `PageHeader` and the `md:grid-cols-2 xl:grid-cols-3` card grid). A server component with no data; `role="status"` inside an `aria-live="polite"` wrapper, with a visually hidden "Loading…".
- `error.tsx` (root and `(app)/`) — client error boundaries (`error`, `unstable_retry` props, per Next 16). They log with `console.error` in an effect and show `EmptyState` ("Something went wrong", Try again, Go home). The message and stack are never shown. `(app)/error.tsx` renders inside the app shell; the root one sits on the cream background with `BrandMark`.
- `not-found.tsx` (root and `(app)/`) — 404 screens on `EmptyState`. Root: "We couldn't find that page" with Go home, centered with `BrandMark`, outside the shell. `(app)/`: same title, with Go home and "See your families" (`/families`), inside the shell (for example unknown member ids via `notFound()`).

`/invite/[token]` and `/join/[inviteCode]` sit outside `(app)/` so unauthenticated users land on the page first, then are sent to login/signup with `?next=` redirect param.

## Design decisions

**Why gifts are personal, not family-scoped**: Each gift belongs to its owner, not to one family. A user in multiple families (e.g. own family + in-laws) shares the same wishlist with all of them — one list per person, not one per family pairing. Visibility and the surprise-preservation guarantee are enforced at the RLS layer via shared `family_members` rows between the viewer and the owner (see `0005_personal_wishlists.sql`), not via a `family_id` column on `gifts`.

**Why sign-up and forgot-password answer the same for every email**: anti-enumeration. Better Auth requires email verification, which makes `sign-up/email` answer an existing email with a synthetic user shaped like a new one (no session either way); the real account gets an "already registered" email instead. `request-password-reset` answers the same whether or not the email exists. Auth emails are sent without awaiting them, so timing doesn't tell either. `tests/e2e/auth.spec.ts` pins the sign-up behavior by shape.

**Why self-hosted Better Auth, and why bcrypt**: spec D3 (`docs/superpowers/specs/2026-10-07-aws-neon-migration-design.md`): no MAU billing, auth data branches with the database, testable locally. bcrypt (cost 10) matches Supabase's hashes, so existing users keep their passwords at the Phase 3 import. Standing duty: ship Better Auth security releases the same week.

**Why three database roles, and why RLS stays**: surprise preservation is a database guarantee, not an app convention. `app_user` (every app query) can't read Better Auth's tables and can't skip RLS; `auth_service` (Better Auth) can't read gifts or claims; `neondb_owner` only runs migrations. Invite and join acceptance, which used Supabase's service role to bypass RLS, are now SECURITY DEFINER functions that check their own inputs (`tests/db/functions.test.ts`). `tests/db/policies.test.ts` proves the guarantees against the real migrations on every PR.

**Why the rate limiter runs in prod only, and its open issue**: Better Auth allows 3 sign-ins per 10 seconds per IP. Dev and staging see only Patrick and the e2e suite, which signs in many times a minute from one address. In prod, Better Auth trusts `X-Forwarded-For` only when it holds one address; behind CloudFront and a Function URL it may hold more, which would put every user in one shared bucket. How prod gets a trustworthy client IP is decided before the Phase 3 cutover.

**Why the deep health check needs CloudFront to forward `authorization`**: CloudFront passes only allow-listed headers to the Lambda; without it the smoke tests' bearer token never arrives and the check silently answers the shallow way. The list is at CloudFront's limit of 10.

**Why join codes are normalized**: `/join/[inviteCode]` now trims and lowercases codes before lookup and uses case-insensitive matching. This prevents false "invalid link" states when shared codes are copied with casing differences. `normalizeJoinCode()` accepts both lengths: new codes are 32 hex characters, and a family that hasn't reset its link still has a 12-character one (made by the old default, or set by hand).

**Why the app rate-limits joins and invites** (#154): Better Auth's limiter covers only `/api/auth`, and without a limit anyone could try join codes as fast as they liked, or use a verified account to send unlimited Lumen email. Counters are in Postgres (`app_rate_limit`), so every Lambda instance shares them. The limits (`LIMITS` in `src/lib/rate-limit.ts`):

| Action | Per user | Per IP (prod only) | Other |
|---|---|---|---|
| Join preview (`/join/<code>` page) | none | 30 per 15 minutes | |
| Join (`POST /api/join/<code>`) | 10 per 15 minutes | 20 per 15 minutes | |
| Invite email (`POST /api/families/<id>/invite`) | 10 per hour and 30 per day | 20 per hour | 20 per family per day |

A wrong code still counts, which is what slows guessing. An invite that `create_invite()` refuses (not a member) rolls back and doesn't count, so nobody can use up another family's daily cap. Per-user and per-family limits run in every environment, so dev and staging run the same path as prod; e2e makes a fresh user and family per spec and never reaches them. Per-IP limits run in prod only, like Better Auth's: outside prod every visitor is Patrick or the e2e suite from one address, and a local run has no CloudFront, so everyone is `127.0.0.1`. When `ORIGIN_VERIFY_SECRET` is set and a request has no trustworthy address (it skipped CloudFront), the routes answer 403 and the page says it can't check the link.

**Why shadcn/ui v4 components don't support `asChild`**: v4 uses Base UI primitives instead of Radix UI. The `Button` component was replaced with a Radix-based implementation to restore `asChild` support. The `DropdownMenu` trigger and items use `onClick` + `router.push()` for navigation instead.


**Why some JSX text has an explicit `{" "}`**: Turbopack in Next 16.2 drops the leading space of a JSX text chunk that follows a tag or `{expression}`, contains an HTML entity (`&apos;`) and runs to a line break. Write the space as `{" "}` in that case. See G13 in `docs/ui-overhaul/discovery.md`.

**Why dashboard greeting is client-rendered**: The greeting period (morning/afternoon/evening) is computed in a Client Component after mount so it reflects the viewer's local time rather than the server timezone; the server markup is the neutral "Hi".

**Dashboard data**: per-family counts come from `listMyFamilies().member_count`. Each family card's avatar stack is that family's own people: the `fellowMembers` rows whose `family_id` is the card's, before the de-duplication (up to three, never you). "Your people" comes from `fellowMembers(tx, id, 50)` de-duplicated by `user_id` in the page (the query limits rows, not people, so it can still undercount past 50 rows; fixing that is a data-layer follow-up). Recipient names on claims are looked up in that people list by the gift's `owner_id` (`recentClaimsBy` returns no owner name); with no match the row omits "for <name>".

**Gift form (`src/components/gifts/gift-form.tsx`)**: shadcn `Form` + `giftSchema`, shared by `/gifts/new` and `/gifts/[giftId]/edit` (both: `BackLink`, `PageHeader`, `max-w-xl`). `validations.ts` is unchanged because the API validates with the same schema, so the form tidies values itself: on blur a link gets `https://` and a price loses `$`, commas and spaces, and `tidyThenSubmit` repeats that before `handleSubmit` so Enter without blurring works. The picture link sits behind a "Use a different picture" disclosure (open by default when the gift has an image; a scrape opens it) with a `GiftImage` preview via `useWatch`. Cancel is a link to `/gifts`.

**Why URL scraping runs server-side**: The "Got a link? Paste it here" box ("Fill it in") on the add-gift form posts the pasted URL to `/api/gifts/scrape`, which fetches the page server-side (browser fetches are CORS-blocked on most retail sites) and extracts details with `cheerio`. The route guards against SSRF by resolving the hostname and rejecting loopback/private/link-local/cloud-metadata addresses, and caps fetch time (8s) and body size (2 MB).

**Scraper extraction chain** (`scrapeGift`): sources are tried in priority order and the first hit wins, so coverage degrades gracefully:
1. **Site-specific** — Amazon DOM extraction (see below).
2. **JSON-LD** (`schema.org/Product`) — the web standard retailers embed for Google rich results. Yields a clean name, image, price, and description in one shot, and is often the *only* place a price is exposed (e.g. Uncommon Goods). Parsed from all `<script type="application/ld+json">` blocks, walking `@graph` and arrays; malformed blocks are ignored.
3. **Open Graph / Twitter / standard meta tags** — name, image, description, and `product:price:amount`.
4. **`<title>` / `<h1>`** — last-resort title.

Scraping is best-effort. Empirically, common sites fall into three buckets: (a) good structured data → name+image+price work; (b) reachable but JS-rendered (Nike, Allbirds, Target) → name+image only, price is JS-loaded and absent from initial HTML; (c) **hard-blocked** (Etsy, REI, West Elm, Best Buy, etc.) → return 403/429/503 to datacenter-IP requests regardless of User-Agent, so nothing is extracted. In every partial/failure case the form falls back to manual entry (the pasted link is still saved). Defeating bucket (c) or getting price from bucket (b) would require a headless browser and/or residential-IP proxy or a paid scraping API — deliberately out of scope. Scraped descriptions are capped at 1000 chars to satisfy the gift form's validation. Scraped prices go through `tidyPrice()`: a bare number, whole dollars without cents ("140" for a store's "140.0") and anything else with two ("34.50"), so the form's price box shows what a person would type.

**Why Amazon has a dedicated extractor**: Amazon is the most common source, but its product pages ship generic/empty Open Graph tags ("Amazon" title, logo image) while the real data lives in the DOM. `scrapeGift` detects Amazon hosts (`amazon.*`, `amzn.*`, matched against the post-redirect host so `amzn.to` short links work) and reads the title from `#productTitle` and the image from `#landingImage`'s `data-old-hires` / `data-a-dynamic-image` (largest variant). These site-specific values take priority over the generic meta-tag fallback. **Amazon price is not scrapable** from the initial HTML — it's lazy-loaded via a later AJAX call — so price comes back empty on Amazon and the user enters it manually. Server-side fetches with our bot User-Agent currently receive the full product page (not the captcha variant); if that changes, title/image will degrade to empty and fall back to manual entry.

**Why `images.unoptimized` is set**: Scraped product images come from arbitrary retailer domains that can't be predicted, so a `remotePatterns` allowlist would be too brittle. `next.config.ts` sets `images.unoptimized: true` so `next/image` serves any external image as-is (Next otherwise `400`s images from unconfigured hosts). Trade-off: Next's image optimizer/proxy is skipped for all images.

**Why `is_family_member()` exists**: querying `family_members` inside the `family_members` SELECT policy caused PostgreSQL RLS recursion (carried over to Neon unchanged) (`infinite recursion detected in policy for relation "family_members"`). The SECURITY DEFINER helper lets policies check membership without recursive policy evaluation.

**Why families are created through `create_family()`**: inserting a family and reading it back under RLS depends on the owner membership already existing. The definer function inserts the family (a trigger adds the owner) and returns the new id.

**Why non-prod never touches prod data**: dev and staging are their own Neon branches (`dev`, `staging`), created empty from an empty `production` branch, so no real wishlist or email exists outside prod. Each environment's connection strings live under its own SSM prefix, and the e2e suite refuses the production branch. (Before Phase 2, a separate staging Supabase project played this role; prod still uses Supabase until the cutover.)

**Why the app runs on AWS instead of Vercel**: part of the migration in `docs/superpowers/specs/2026-10-07-aws-neon-migration-design.md` (issue #50), pulled forward when the repo moved to the `pateastudio` organization: Vercel's Hobby plan doesn't build organization repos. OpenNext turns the Next.js build into a Lambda bundle. `pnpm-workspace.yaml` sets `nodeLinker: hoisted` because the zipped bundle can't follow pnpm's nested symlinks; `scripts/check-bundle.sh` proves each build loads.

**Why signed-in links don't prefetch**: every route under `(app)` is dynamic and per user, so each prefetch is a full Lambda request with its Supabase calls. Next prefetches every visible `<Link>`, and on Lambda a page view fanned out into 10 to 20 requests, which started cold instances and made clicks take 2 to 3 seconds. Every `<Link>` in the signed-in area sets `prefetch={false}`, and so does every one on the public pages (`src/components/marketing`, `auth`, `legal`, `src/app/page.tsx`, `src/app/(legal)`); `tests/unit/link-prefetch.test.ts` enforces it.

**Why pages call `getCurrentUser()`**: the `(app)` layout and each page both need the user. `getCurrentUser()` (React `cache()`) reads the Better Auth session once per request, and with the cookie cache that normally means no database call. API routes use `requireUser()`. `tests/unit/current-user.test.ts` keeps pages off the raw session API.

**Naming and titles**: the app is "Lumen" in all UI text and emails (the domain `lumenlist.app` stays wherever a URL shows). A person's list is "my list" / "Rose's list", the things on it are "gifts", people are "family". Never "wishlist" or "Lumen List" in user-facing text. The root layout sets `title: { default: "Lumen", template: "%s · Lumen" }`; each page exports a static `metadata.title` (family hub and settings stay static to avoid a second data load). Error toasts read "Couldn't … Try again." rather than "Failed to …".

**JSX space bug**: Turbopack drops the leading space of a text chunk that follows a tag or `{expression}`, holds an entity (`&apos;`) and runs to a line break. Write `{" "}` explicitly there.

### Onboarding tour (`src/components/onboarding/`, issue #98)

Everyone is offered a walk once: a welcome card, four coach marks on the real signed-in screens, then a hand-off to First Steps (the checklist that follows; see below).

- **Where the state lives.** The `(app)` layout reads the person's `onboarding` row with `getTour` and hands it to `TourProvider`, which keeps this tab's copy (shown at once, sent behind through `PATCH /api/onboarding`) and exposes `useTour()` (`{ data, state, phase, send }`, null once the tour is over). `tour-state.ts` holds the rules as pure functions (`phaseOf`, `applyEvent`, `mergeState`, `trackFor`, `pickPerson`, `buildTasks`); `tour-events.ts` sends events in order and retries; `tour-local.ts` (`useLocal`, `clearLocal`) keeps per-browser bits. Which stop of the walk someone is on is only in `sessionStorage` (`walk-step`, `walk-missed`), so a reload in the same tab resumes there and nothing is written to the database until the walk ends.
- **The walk** (`walk/walk.tsx`, `walk/stops.ts`) is drawn by `TourUi` while `phase` is `walk`. It is built on `src/components/ui/tour.tsx` (generated by `shadcn add @diceui/tour`; its lint exceptions are in `eslint.config.mjs`, so a regenerate stays a clean diff). That library knows one page, so `walk.tsx` adds the page-to-page part: each stop names its page and its anchor, and the controller pushes there, waits up to four seconds for the anchor, scrolls it clear of the sticky header and the phone tab bar, then shows the card. A stop whose anchor never turns up is skipped and the "Step n of m" count shrinks to match. `Walk` renders nothing on the server or on the first browser pass, because the stop number can't be read yet.
- **The stops.** With a family: the "My list" tab on Home, "Add a gift" on `/gifts`, an "I'll get this" button on the list of the first person with something up for grabs (`pickPerson`; falls back to the filter, then the empty card), and that list's surprise note. With nobody to share with yet (no family, or a family with only them in it): the "My list" tab, "Add a gift", the Family tab ("Start a family here", or "Open your family here" when they already have one), and Home's surprise note.
- **Anchors.** Stops find their targets by `data-tour="<name>"` on the real screens (`findAnchor` in `anchors.ts` takes the first visible match, since the header tabs and the phone tab bar carry the same names) and by `[data-claim-state="available"] button`. Renaming or removing one silently drops that stop; the walk carries on without it.
- **The walk never ticks a step.** It writes only through the callbacks `TourUi` gives it: skipping ("Not now", Skip, Escape) sends `walk_skipped`, finishing sends `walk_completed`, and `steps_completed` follows only when nothing is left on the checklist (then the walk ends on a "You know everything" card instead of the hand-off). `TourUi` also notes the page the walk left them on (`left-on`) so that list will not count as a peek. Escape between two stops ends the walk while the next page is still on its way, so `Walk` hands `onSkip` that page and `TourUi` notes it too (`walk-heading`, also `sessionStorage`); when it arrives, `Steps` makes it the new `left-on`. Without that, skipping on the way to someone's list ticked "Peek".
- **The hand-off** card points at the First Steps pill (`[data-first-steps-launcher]`). The pill is drawn as the hand-off comes up, so the walk gives it 200 ms (`PILL_WAIT`) to appear; if it is still not on the page then, the walk ends without the card. `useWalkAtHandoff(userId)` tells the pill it should show under the card.
- **Replay** (`replay-tour-card.tsx`, `ReplayTourCard` on `/account`, for everyone, finished or not): "Show me around again" sends `restart` (which clears the walk, the hints and a hidden or finished checklist, and keeps every tick: the ones with data behind them, and `peeked_at` and `secret_seen_at`, since a replay undoes nothing the person did; owner's decision, 2026-10-12), forgets what this browser kept (`clearLocal`) and calls `router.refresh()` in a transition, so the button is disabled only while the request or the refresh is running. The layout then reads a new `run`, `TourProvider` remounts, and the walk (`state.replay`) starts at stop one with no welcome and goes to Home by itself. The card must not push as well: in Next 16 a `router.push()` and a `router.refresh()` asked for together reach the browser as one `replaceState`, so Back from Home would skip Account. Someone with all four steps done therefore has nothing left after a replay: the walk ends on "That's it. You know everything." with no hand-off and no pill, and `walk_completed` and `steps_completed` go together. (The track is chosen afresh, so someone who was on their own and now shares a family gets the invited steps.) This is what the sheet and the celebration mean by bringing the steps back "from your account".
- **First Steps** (`steps/steps.tsx`, `views.tsx`, `steps-sheet.tsx`, `hint.tsx`, `inline-hint.tsx`, `bits.tsx`) follows the walk while `phase` is `steps`: a pill (`data-first-steps-launcher`) above the phone tab bar, bottom right on wide screens, that opens a sheet (`data-first-steps-panel`, `data-view` `list`, `secret` or `done`) of four tasks from `buildTasks`. Ticks come from real data, plus `peeked` (they opened someone's list themselves, or asked for it from the sheet; the list the walk left them on, `left-on`, does not count by itself) and `secret_seen` (they opened the explainer). `steps_shown` fixes the track the first time the pill appears. Finishing all four shows the celebration and sends `steps_completed` when it is closed; "Hide these steps" sends `steps_hidden`. `StepsSheet` is built from Base UI `Dialog` parts, not shadcn's `SheetContent`, because it has to stop above the tab bar (`modal="trap-focus"`: a dialog for the keyboard, the tabs still work by touch). Hints: `Hint` is a floating bubble on "I'll get this" (`data-first-steps-hint`); `TourHint` is a note in the page's own flow, so it covers nothing, used inside the gift form's paste box (`data-tour-hint="add"`) and under the buttons on the family page (`data-tour-hint="invite"`; a bubble there hid the family's name on phones and the "Everyone's lists" heading on wide screens). The invite note shows on the page of every family they open, not only their first, until "Got it" or until someone else has joined one of their families. Each goes for good with "Got it" (`hint_read`) or when its task is done. During the walk only the pill is drawn (`show="launcher"`), and only while the hand-off card points at it; the walk gives it 200 ms to appear. What is only decoration (`last-done` for "Nice one", `head-start` for "Already done. Nice.") stays in `localStorage`. The keyframes (`fs-*`) are in `globals.css`.
- **Keyboard and motion.** Tab stays inside the welcome, each stop card and the sheet; Escape skips the walk, is "Later" on the hand-off and closes the sheet. When the walk ends (skip, "Not now", "Later", "Done"), `TourUi` puts focus on the pill, or on the Home tab when there is no pill; closing the sheet returns it to the pill. Safari moves between buttons with Option+Tab, which the tour library's trap ignores, so `walk.tsx` wraps that itself (`wrapOptionTab`). With reduced motion nothing moves: the cut-out cuts, the cards and the welcome appear in place, the pill and the ticks don't bounce (backdrops still fade). The card's arrow, the dots, the emoji and the icons are hidden from screen readers; every card is a `dialog` named by its heading, and the pill is a button named "First steps, n of 4 done".
- **E2E** (`tests/e2e/onboarding.spec.ts`, at 390px, with a family name of exactly 100 characters that ends in one 46-character word with nothing to break on, and a sideways-overflow check at each step): an established person sees nothing; an invited person gets the welcome, four stops and the hand-off, with nothing ticked and the welcome never redrawn; opening a list yourself is a peek; adding a gift ticks; hiding is remembered in a second browser; a restart that fails shows its toast and changes nothing; replay from Account brings the walk (no welcome, not for a frame) and the pill back with one history entry, and Escape on the walk leaves focus on the pill, with what they had done still ticked; a replay with every step done ends on "You know everything", writes both endings and leaves nothing of the tour after a reload; someone with no family is walked through their four stops (the cut-out is checked against each stop's anchor, the Family tab and Home's surprise note among them) and gets the other steps; "Not now" leaves the pill; Escape on the way to someone's list (the list's page held back at the network so "One sec…" stays up) ticks nothing, in the sheet or in the database; the invite note shows on a new family's page and stays gone after "Got it" and a reload. `backend.tourRow(user)` reads the person's `onboarding` row for those checks. The stops' words are unit-tested (`tests/unit/tour-stops.test.ts`). `createUser(label)` marks the tour over so other specs never meet it; `createUser(label, { tour: "fresh" })` makes someone who has never seen it. The walk keeps `data-walk` (`welcome`, `finish`, `moving`, `card`, `ring`) and `data-walk-step` for specs.
- **Known limits** (after the final pass, 2026-10-12):
  - A real screen-reader pass (VoiceOver on an iPhone) has not been done. Checked by machine only: roles, names and what is hidden. One thing to listen for: during a stop the page behind the card is covered and can't be clicked, but it is not hidden from a screen reader (the card has no `aria-modal`), so swiping can leave the card.
  - `router.refresh()` can hang until the next interaction (issue #128, a React and Next bug, not the tour's). Here it can leave "Show me around again" disabled, or a checklist tick waiting, until the person does something else. The data is saved either way.
  - Escape between two stops, then a reload before the next page arrives (a window of under a second): `walk-heading` is still remembered, so the first time they open that page themselves is taken for the walk's move. If it is someone's list, the peek ticks on their next visit.
  - While First Steps is running, a spacer at the end of the page (`h-14`, so the pill never rests on a form's last button) makes pages shorter than the screen scroll by 56px on phones.

### Legal pages (issue #97)

The Privacy Policy and the Terms are Markdown files in `docs/legal/`, and the Markdown is the source: nothing is copied into code, and the files are never reworded to suit the renderer. `/privacy` and `/terms` read them at build time through `parseLegal`, which supports only the subset listed under Key files and throws on anything else, so a document that uses more fails the build instead of rendering wrong.

The documents are published: `LEGAL_EFFECTIVE_DATE` in `src/lib/legal/published.ts` is `"2026-10-13"`. That one switch controls everything. If it were `null`: `/privacy` and `/terms` answer 404 on every deployed build (under `next dev` they show, marked as not published); the footer of the front page and of the legal pages would have no Privacy, Terms or copyright line; the account page no Privacy and Terms links; and `LegalLine` would render nothing on sign-up, invite and join. With it set, all of those show, and each page says "Effective October 13, 2026". `docs/legal/PUBLISHING.md` records what was made true before publishing (30-day backups for `db/lumenlist/` in the S3 lifecycle, 30-day log retention in Terraform, and the two sign-in cookies Section 7 describes), how to change a document later, and the promises the documents make. `tests/unit/legal-published.test.ts` renders the published look with the date mocked (effective line and title on both documents, the sign-up line, the footer with and without `legal`).

### Theme tokens (`src/app/globals.css`)

Sunday Picnic is the default theme (three themes: Picnic, Confetti, Patea). Its tokens are declared once, under the combined selector `:root, [data-theme="picnic"]`; Confetti is the second theme, a `[data-theme="confetti"]` block with the same names and new values (opt-in; picker on `/account`). Switching is next-themes' `ThemeProvider` in `layout.tsx` (`attribute="data-theme"`, `themes=THEME_IDS` (picnic, confetti, patea), `defaultTheme=DEFAULT_THEME` (both from `src/lib/themes.ts`), `enableSystem={false}`, `storageKey="lumen-theme"`, `suppressHydrationWarning` on `<html>`); its inline script sets the attribute before paint, so signed-out pages and reloads show no flash. There is no dark mode. Confetti's fonts (Fredoka, Nunito) are `next/font` variables with `preload: false`, so no preload links; the files download only when a rendered element uses them (Picnic users only fetch them on `/account`, where the preview renders Fredoka). `--radius-button` (Picnic `calc(var(--radius) * 0.8)`, Confetti `999px`) is read by `Button` (`rounded-button`) and `ink-button`; `--press-shift-x` lets Confetti press straight down (0px). Confetti sets `--border-strong` to its soft border color, `--shadow-card: none`, and a pressable `--shadow-button` of darker primary. The toaster is pinned `theme="light"` (next-themes would hand Sonner the theme name). Theme-varying tokens: `--font-display`, `--font-sans` (mapped from the `next/font` variables `--font-bricolage` and `--font-dm-sans` set in `layout.tsx`), `--radius`, `--border-strong` (ink outline), `--shadow-card`, `--shadow-button` (offset "sticker" shadows), `--hero`, `--tone-0..3-bg` / `--tone-0..3-fg` (avatar and gift-tile tones), `--success`, `--destructive-foreground`, plus the shadcn set. Tailwind sees them through `@theme inline` (`bg-success`, `text-destructive-foreground`, `border-border-strong`, `bg-hero`, `bg-tone-0-bg`, `shadow-card`, `font-display`). Components must use tokens, never a Picnic literal. `--muted-foreground` is at least 4.5:1 on background, card and muted. Every theme block lists the same tokens in the same order with section comments (fonts, surfaces, brand, lines, status, shape and depth, hero and tones, sidebar and charts); a comment at the top of the theme section in `globals.css` explains how to add a theme and how to change the default (move `:root,` to another theme's selector and change `DEFAULT_THEME` in `src/lib/themes.ts`). There are no `ds-*` or `t-*` classes and no legacy `--ink*`, `--surface*`, `--hairline*` or `--primary-soft*` variables: use Tailwind classes and the tokens. **Ink treatment** (Picnic's outline and offset shadows) comes only from tokens `--ink-width`, `--border-strong`, `--shadow-card`, `--shadow-button`, `--shadow-button-pressed`, `--press-shift`, through the `ink-card` and `ink-button` utilities in `globals.css`. It is opt-in: `<Card variant="ink">`, `<Button variant="ink" | "ink-outline">`, and the default look of the new shared pieces; existing Card and Button usages are unchanged. `Button size="lg"` is now h-12 with `text-base`, and Button focus is a 3px `--ring` ring with an offset.

**Confetti check (task 14)**: new theme tokens, all with Picnic values that reproduce the old look (pixel-identical screenshots): `--shadow-button-outline` / `--shadow-button-outline-pressed` (outline ink buttons; Confetti uses neutral `--input` instead of darkened `--primary`), `--button-border` (filled ink button border; Confetti `transparent`, so no light ring) and `--button-outline-border`, `--toggle-on` (selected toggle fill; Picnic `--muted`, Confetti `--secondary`, read by `toggle.tsx`), and `--hero-image` (`none` in Picnic, the gradient in Confetti; `--hero` is now always a solid colour, because a gradient is invalid in `background-color`). `bg-hero` is a custom `@utility` in `globals.css` (colour plus image) instead of the `@theme` colour. `ink-button-outline` is the utility the `ink-outline` variant adds. Confetti values darkened for WCAG AA: `--primary`/`--ring` `#DB2955`, `--success` `#0D8075`, `--input` `#8F85A6` (3:1 field boundary).  No component hard-codes a color. The overhaul's history is in `docs/ui-overhaul/` (`plan.md`, `discovery.md`).

## Environment variables

In deployed environments these come from SSM (one prefix per environment) through Terraform into the Lambda; `NEXT_PUBLIC_APP_URL` comes from the hostname, and `BETTER_AUTH_SECRET` and `HEALTH_TOKEN` are generated by Terraform. Locally they come from `.env.local` (the Neon dev branch). See `docs/DELIVERY.md`, "Settings".

| Variable | Used by |
|---|---|
| `DATABASE_URL` | `app_user`, pooled: every app query (`src/lib/db`) |
| `AUTH_DATABASE_URL` | `auth_service`, pooled: Better Auth only |
| `DATABASE_URL_UNPOOLED` | `neondb_owner`: `scripts/migrate.sh` only (read from SSM, never in the Lambda) |
| `BETTER_AUTH_SECRET` | Signs sessions and the cookie cache |
| `NEXT_PUBLIC_APP_URL` | Better Auth's base URL and email links |
| `APP_ENV` | `prod`, `staging` or `dev` (anything else counts as dev): the mail guard, Better Auth's rate limiter and the app's per-IP limits |
| `NON_PROD_MAIL_TO` | Outside prod, the only addresses that receive email |
| `HEALTH_TOKEN` | Unlocks the deep `/api/health` check |
| `RESEND_API_KEY`, `RESEND_FROM_EMAIL` | Email |
| `E2E_DATABASE_URL`, `E2E_APP_DATABASE_URL` | The e2e suite's backend (owner unpooled, `app_user` pooled) for dev or staging; never prod |

Before the 2026-10-09 cutover, prod ran v0.3 with the Supabase variables (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`). They stay in SSM as the rollback path until Supabase is retired (#46).

| Token | Picnic | Confetti | Patea | Read by |
|---|---|---|---|---|
| `--display-weight` | 800 | 800 | 500 | page and section headings: `font-(weight:--display-weight)` |
| `--display-weight-soft` | 700 | 700 | 500 | names, gift titles, avatar initials: `font-(weight:--display-weight-soft)` |

| `--primary-hover` | primary at 90% | same | `#33192F` | `Button` default and ink (`hover:bg-primary-hover`) |
| `--danger-surface` | `var(--card)` | same | `#EBE2EA` | danger buttons |

| `--hover-lift` | 0px | 0px | 1px | `ink-button` hover rise |
| `--press-scale` | 1 | 1 | 0.985 | `ink-button` press squeeze |
| `--button-transition` | transform, shadow, bg, color | same | + translate, scale | `ink-button` transition-property |

`prefers-reduced-motion` zeroes `--hover-lift` and `--press-scale` for every theme (a media block after the theme blocks). `tw-merge` understands `font-(weight:--x)`, so these override `font-medium` and friends in `cn()`.

**Making Patea the default is two steps**: (1) move `:root,` from Picnic's selector to `[data-theme="patea"]` in `globals.css`; (2) set `DEFAULT_THEME = "patea"` in `src/lib/themes.ts` (layout passes it as `defaultTheme`; the picker falls back to it). Optional follow-up for performance, not correctness: drop `preload: false` from Newsreader and Instrument Sans in `layout.tsx` and add it to Bricolage Grotesque and DM Sans, so the new default's fonts get preload links. The picker previews render all three themes, so on `/account` every theme's fonts are fetched regardless.
